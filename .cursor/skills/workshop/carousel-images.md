# 公众号贴图 · 只出图

贴图模式**只做图**，不写配文、不生成 `{slug}.carousel.txt`、不跑 `--platforms carousel`。

成稿根目录：`output/wechat-images/`。气质标杆：[`data/assets/_style/`](../../../data/assets/_style/)（`flow.png` / `table.png` / `hero.png`）。

## 目录结构（草稿与成图同批）

同一批贴图共用一个日期目录，**草稿和 PNG 放一起好找**：

```
output/wechat-images/2026-09-11/
  draft/                 # HTML 草稿（先审）
    01-hero.html
    02-features.html
  01-hero.png            # 确认后截出的成图
  02-features.png
```

| 情况 | 批次目录 |
|------|----------|
| 当天第一次 | `output/wechat-images/2026-09-11/` |
| 同日已有该日期目录，再出一批 | `output/wechat-images/2026-09-11-14-06/` |

规则：

- 默认目录名 = 当天 `YYYY-MM-DD`
- 若该目录**已存在**，追加本地时间写成 `YYYY-MM-DD-HH-MM`（24 小时制；**勿用冒号**，Windows 路径非法）
- 先建批次目录 → HTML 写入其下 `draft/` → 等人审 → PNG 写在批次目录根下（与 `draft/` 同级）
- 同一批确认出图共用一个目录；不要把同一次任务拆到两个时间戳夹
- HTML 引用 `data/assets/` 时注意相对路径深度：从 `…/YYYY-MM-DD/draft/*.html` 一般为 `../../../../data/assets/…`

汇报示例：`output/wechat-images/2026-09-11/01-hero.png`（草稿在同夹 `draft/`）。

## 流程

1. Glob `data/assets/`，按主题文件夹名匹配；命中则 Read 该夹 README，**构图里真正用上** logo / 立绘 / Q 版（不要只在角落塞一个小标）。
2. 读参考材料，按下方「内容怎么拆」组织成图（张数自定）。
3. 确定批次目录（见上），用 **HTML** 写草稿到 `{批次}/draft/`（竖版约 **1080×1440**，中文清晰）。
4. **停下来等人审**：把 `draft/` 路径发给用户，说明共几张、每张在讲什么；**在用户明确确认（如「可以出图」「通过」）之前，禁止截图、禁止写 PNG**。用户改了 `draft/` 里 HTML 后，再按最新稿出图。
5. 用户确认后，HTML → 截图，PNG 落到**同一批次目录根下**（与 `draft/` 同级），文件名说清顺序和内容，如 `01-routing.png`。
6. 纯贴图不必写 IR、不必 CLI。若同时要长文/小红书，IR 只服务那些平台。

## 内容怎么拆

### 有分区的更新说明（GitHub Release / changelog 等）

任意仓库通用。按源文分区出图（有中文用中文；仅英文则意译对应）：

1. **新增功能**
2. **体验优化**
3. **问题修复**
4. **其他变更**（Chores / Breaking / Migration 等归此类）

可选最前一张**薄封面**（版本号、一句定位、分区导航 + 角色）。一类一屏不够就拆同标题多屏，不要为凑张数硬塞，也不要压成「三四个大卖点海报」。

**措辞**

- **尽量保持原文**（优先官方中文；仅英文则忠实意译）。可删 `@contributor`、重复套话。
- **禁止过度缩写**：缩短不得换主语、不得丢关键宾语。  
  反例：「官方适配器仅使用 Messages API，并可通过 Files API 复用已上传图片」→「Files API 上传图片」语义已变，禁止。
- 单条一两行为宜；合并后仍超长则拆回或「主句 + 括号补充」。

**合并与取舍**

- **同类合并**：同一能力面多条合成一条，顿号/逗号串起（如多个侧栏能力合成一条），不必一条一卡。
- **不求全**：读者不在意的小点直接省略（排序微调、极窄场景、纯文案/本地化等）。约覆盖「会改变用法」的六七成即可。
- **优先保留**：可感知新能力、默认行为变化、破坏性改名/迁移、安全/沙箱/数据类修复。
- 某类砍完仍很长 → 脚注「其余见原文」，不做完整 changelog 截图。

### 其它话题

一图一事亦可，常见 2～5 张；卖点/单事件可贴「少而大」。

## 气质（活泼明亮，不要死板）

对标 `_style` 三张，而不是仓库里旧的深色清单图。

- **底**：浅亮（如 `#F7FBFF`），可加淡波浪、光晕；不要大面积黑底、电路纹、编号军规卡
- **色**：品牌色点缀（主题有约定则用资源库色，如 DeepSeek `#4D6BFE`）；卡片圆角、轻阴影
- **字**：图上的字就是给读者看的全部，没有配文托底。更新说明类用分区列表时可更密，但靠「区与区空隙大、条目之间空隙小」保持留白；单事件可贴少而大
- **活**：主动用资源库角色；封面可用大立绘，内容屏可缩成角标/半身把中部留给条目。流程、对照表、列表、网格换着来，不要每张同一模板
- **准**：logo / 立绘用库内文件，禁止自绘已有素材；中文不要用文生图硬写长段

## 构图可以变

同一套气质下换布局，例如：流程块、对照表、大标题+立绘+网格、分区条目列表、Q 版贴纸风。不要做成同一模板填空。

## 自检

- 单独看图能否看懂这张在说什么
- 更新说明类：分区是否对上源文、原文未偏义、同类已合并、鸡毛蒜皮已砍
- 资源库有角色却整组都没用上 → 至少一张用立绘或 Q 版
- 像旧版深色更新日志 → 推倒按 `_style` 重做
- 有 HTML 草稿却未等用户确认就出 PNG → 违规，先审后截
